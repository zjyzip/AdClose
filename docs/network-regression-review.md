# 网络改动复盘与回归修复

## 范围与结论

本轮对照 `b2a137f` 中的原实现，复查了此前两轮未提交的网络修改。此前改动并非局部修补：H1 解析、Conscrypt 入口、Cronet 正文采集、正文跨进程传输、Native SSL 和 H2 生命周期都发生了变化。之前仅凭构建和单元测试就判断“放行不干扰、覆盖完整”，结论过满。

用户报告的实际问题是正文大量缺失，以及原始请求受到影响。以下列出代码上能确认的原因；未把这些原因当作对所有现场现象的完整解释。此前的 H2 测试还把“整连接返回错误”当作正确行为验证，没有检查其他流能否继续，这也是测试通过却仍造成回归的原因；该用例现已改为验证回调匹配不能改变共享连接的原调用结果。

## 前两轮改了什么

| 部分 | 相对原实现的改动 | 本轮处理 |
| --- | --- | --- |
| H1 | 替换为增量状态机；处理连接复用、Chunked、HEAD/204/304、关闭定界正文；加入容量限制 | 保留解析修正；恢复请求体独立采集和上报，响应头提前上报；保留无 Host 请求 |
| 请求展示 | 请求头到达就记录；同 requestId 更新原行；DNS 聚合计数 | 保留；修复详情页仍停留在打开时快照的问题 |
| 上报去重 | 用递增阶段抑制重复广播 | 改为已观察字段的集合，允许请求体在响应之后到达 |
| 正文传输 | 从一次 Binder insert 改为 128 KiB 分块上传，并校验上传 token/UID | 保留；复用已经生成的正文 URI，避免一个请求的多个更新重复上传同一正文 |
| 正文缓存 | 增加总内存限制，超过单体上限时整体丢弃，避免截断压缩内容 | 保留完整性保护；扩大采集过程的并发预算，说明仍有缓存容量和期限边界 |
| Java Socket | 更换到增量解析，修正实际读取偏移 | 保留；撤销 Native 开启后直接禁用整个 Java 明文入口的做法 |
| Conscrypt | 扩展 wrap/unwrap 重载和 FD Socket，改按实际消费/产出的缓冲区采集 | 保留实际缓冲区采集；使用模块自己的锁，不再锁应用的 connection 对象；Java 调用期间仅抑制该线程的 Native 重复采集 |
| Cronet | 从主动读取/关闭应用响应流改为记录应用实际读取的数据 | 保留旁路方式，不恢复主动消费响应流 |
| SSL Hook | 移除把 NativeCrypto JNI 函数当作标准 SSL 函数挂钩的代码；调整错误值、清理和 fd 身份 | 保留 ABI、引用和 fd 身份修正；撤销必须同时解析到 free/get_error 才能采集读写的门槛 |
| H2 传输 | 命中某个流后终止整条 TLS 连接 | 撤销：底层 H2 只采集，不再向原调用返回人为连接错误，也不向 TLS 注入 RST |
| H2 拦截 | 原入口混合了协议观察和传输阻断 | OkHttp 的 newStream、WebView、Cronet 等能识别单个请求的入口执行请求级拦截；仅底层 Native 可见的自定义 H2 实现不能保证按 URL 单流阻断 |
| H2 解析 | 分离双向 header 分片，保留 END_STREAM，更新 HPACK/PUSH_PROMISE、RST/GOAWAY 清理；大幅收紧若干上限 | 保留解析与清理修正；恢复 1000 流容量、扩大连接/元数据预算，DATA 改为流式处理，撤销 256 KiB DATA 帧门槛 |
| JNI | 调整线程附着、局部引用、UTF-8 转换与 Java 数组读取 | 保留；同步请求/响应方向完成状态，正文不再等待两个方向都结束 |

## 已确认并修复的正文缺失原因

1. H1 写方向错误地和响应体开关共用采集条件，请求体被一起关闭。现在写方向独立采集，响应体仍遵循用户开关。
2. 请求体只随最终响应上报。上传成功后没有响应，或者响应一直未结束时，请求体不会出现。现在 H1 上传结束就发出正文更新；H2 分别处理 request/response 的 END_STREAM。
3. 响应先结束、上传后结束时，列表层直接丢弃后来的 `responseCode=-1` 更新，连同请求体 URI 一起丢失。现在只补字段，不降低已收到的响应状态。
4. 初始记录提前出现，但详情页只读 Intent 中的快照，不接受后续正文更新。现在按包名和 requestId 接受更新，补充正文标签，保持当前标签位置；增加小型交接缓存覆盖点击行到注册接收器之间的窗口。
5. 请求体在上传完成、响应头、响应体等多个更新中重复存入 Provider，浪费总缓存。现在同一请求的各方向正文复用 URI。
6. H2 大 DATA 帧及过紧的事件/缓存预算可能停止后续观察。现在 DATA 逐段消费，512 KiB 等合法帧不会因为此前的 256 KiB 限制被放弃。

## 请求受影响的修复

- 取消 H2 规则命中后使整个连接永久进入 blocked 状态的做法；即使回调返回匹配，也不会改变底层 H2 SSL_write/SSL_read 的原始行为。
- H1 响应采集不再在收到响应后重新用规则制造读取错误；请求级拦截仍在发送入口处理。
- 移除对应用 connection 对象的额外同步锁，改用模块私有的观察锁。
- Java 与 Native 同开时，Java 保留自己的采集入口，Native 仅跳过正在由 Java 接管的那次调用；其他 Native 网络调用继续正常采集。

## 没有恢复的危险行为

没有恢复原来主动读取或关闭 Cronet 应用响应流、跨 Binder 发送整块大正文、截断压缩正文、以不兼容 ABI 挂钩 JNI 函数等做法。

## 仍然存在的明确边界

- 关闭“收集响应内容”时不采集响应体；该设置按现有设计在重启目标应用后生效，请求体不受此开关控制。
- 单个正文仍有 5 MiB 上限，Provider 仍有 64 MiB 总缓存及用户设置的保存期限；高流量、超限或过期时，旧正文可能不可用。
- 旁路采集只能看到应用经过已覆盖入口实际读写的数据；Cronet 正文不提前读出，应用未读取或未完整读取的响应不保证有完整正文。
- 只通过底层 Native 暴露的自定义 H2 网络栈，目前只记录流量；没有声称对它实现了无副作用的逐 URL 阻断。
- 宿主 C++ 测试覆盖生产解析器和 Hook 包装器，使用 JNI/ShadowHook 桩；它不能替代目标应用中的实际符号挂钩验证。

## 广播刷屏回归修复

后续检查发现，原来的去重键只覆盖单次 requestId；DNS、CONNECT 和应用重试每次都会生成新的 UUID，所以被拦截的重试会绕出去重。与此同时，接收端每条广播都立即更新列表，导致三组过滤 Flow 反复计算。

现在高频 DNS、CONNECT 和被拦截重试在发送端按稳定目标合并计数；普通请求和正文更新仍按 requestId 合并。通知每 200ms 批量发送，单批正文控制在 192 KiB 内，接收端一次合并整批列表更新。模块执行 Provider 上传和发送广播时启用线程级重入保护，避免 Xposed 把模块自身操作再次当作目标应用网络。

Request 页面菜单现在包含“收集响应内容”复选项。请求列表右侧的次数和 Domain/URL 标签放进同一垂直容器，保持右边缘对齐。
